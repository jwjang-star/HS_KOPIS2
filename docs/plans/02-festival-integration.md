# Phase 2 — 전국 행사·축제 연동

**상태: 조사 중 (API 후보 비교 진행 중, 구현 착수 전)**

## 배경

KOPIS(`pblprfr`)는 "유료 티켓 기반 공연장 공연"만 다룬다. 벚꽃축제·불꽃축제·지역 먹거리축제처럼 무료·야외·지자체 주최 행사는 KOPIS에 아예 안 잡히는데, 지점 주변 유동인구·숙박 수요를 만드는 완전히 다른 카테고리라 새 데이터 소스로 추가할 가치가 크다.

## 후보 API

### 후보 A — 한국관광공사 TourAPI 4.0(KorService2) `searchFestival2`
- data.go.kr 데이터셋 15101578("한국관광공사_국문 관광정보 서비스_GW")
- `https://apis.data.go.kr/B551011/KorService2/searchFestival2`
- 파라미터: serviceKey, MobileOS, MobileApp, _type(json), areaCode, sigunguCode, eventStartDate
- 관광지·숙박·음식점 등 15종 정보 중 하나로 "행사정보"가 포함된 종합 관광 API의 일부
- 지역코드(areaCode)가 KOPIS의 signgucode와 체계가 다름(서울=1, 부산=6, 제주=39 등) → 매핑 테이블 별도 필요. 정확한 값은 `areaCode2` 오퍼레이션으로 직접 조회해서 확정 권장
- 무료, 개발계정 1일 100,000트래픽

### 후보 B — 전국문화축제표준데이터 (사용자 제안, 검증 완료 — 2026-08-05)
- data.go.kr 데이터셋 15013104. 소관 문화체육관광부, 제공 한국관광공사+각 지자체가 표준 스키마로 분기마다 제출
- 파일데이터(XLS/XML/JSON/RDF/CSV)가 기본이지만, data.go.kr이 표준데이터셋을 자동으로 REST OpenAPI로도 변환 제공: `http://api.data.go.kr/openapi/tn_pubr_public_cltur_fstvl_api`
- 필드: 축제명, 개최장소, 축제시작일자, 축제종료일자, 축제내용, 주관/주최/후원기관명, 전화번호, 홈페이지주소, 소재지도로명주소, 소재지지번주소, **위도, 경도**, 데이터기준일자
- **장점**: 위도/경도를 직접 제공 — TourAPI의 areaCode 같은 별도 지역코드 매핑 테이블이 아예 필요 없음(주소 문자열이나 좌표로 바로 판별 가능). 순수 축제만 있어 TourAPI(관광 종합 API의 일부)보다 노이즈가 적고 구조가 단순함
- **단점**: 갱신주기가 **분기(3개월)** 뿐 — KOPIS/공휴일처럼 "매일 갱신, NEW 배지로 즉시 감지"하는 이 시스템의 핵심 패턴과는 궁합이 안 맞음. 새로 생기거나 일정이 바뀐 축제를 최대 3개월 늦게 인지할 수 있음. 지자체 제출 성실도에 따라 지역별 커버리지 편차도 있을 수 있음(예: 소규모 축제가 아예 누락됐을 가능성)
- **미확인**: 이 auto-생성 OpenAPI가 날짜범위/지역으로 서버사이드 필터링을 지원하는지, 아니면 페이지네이션만 되고 전체를 받아 클라이언트에서 걸러야 하는지는 실제 키 발급 후 라이브 호출로 확인 필요(표준데이터 auto-API는 통상 필터가 빈약한 경우가 많음)

### 참고 — 전국공연행사정보표준데이터 (15013106)
전국문화축제표준데이터와 형제격인 표준데이터셋(공연/행사 전반). 이번 조사에서 깊이 보지는 않았으나, KOPIS와 커버리지가 겹칠 가능성이 있어 필요시 추가 검토 대상으로만 메모.

### 참고/보류 — 문체부 문화예술공연(통합) API (15121487)
- 연극/뮤지컬/오페라/콘서트/전시 등을 통합 제공하지만 KOPIS 커버리지와 상당 부분 겹침 — 우선순위 낮음

## 현재 판단 (2026-08-05)

핵심 트레이드오프는 "위경도 제공 + 구조 단순(B)" vs "갱신 빈도 + 서버사이드 필터링(A로 추정, 미확정)". 이 시스템의 정체성이 "매일 갱신되는 KOPIS 데이터에서 NEW를 즉시 잡아내는 것"이라는 점을 고려하면 분기 갱신인 B 단독으로는 핵심 패턴과 어긋난다. 다만 B의 위경도 필드는 지역 매핑 부담을 크게 줄여주는 실질적 이점이라 버리기 아깝다.

→ 두 후보를 배타적으로 택일하기보다, **B(전국문화축제표준데이터)로 구현 부담이 적은 프로토타입을 먼저 만들어보고, 갱신 빈도가 실제로 문제 되면 A(TourAPI)로 교체하거나 병행**하는 단계적 접근을 제안. 단, B의 auto-API가 서버사이드 필터링을 지원하는지부터 실제 키로 확인하는 게 다음 액션.
